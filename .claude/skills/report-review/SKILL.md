# 业务报告交付前审阅

## 何时使用

- 把 HTML、Markdown 或飞书文档发给业务方之前。
- 用户说「术语太多」「看不懂」「AI 味太重」。
- 洞察报告、VOC 报告、成果总结第一次交付。

不用于：工程文档、API 文档、内部复盘。那些按 STE 标准写即可。

## 第一步：写清读者与决定

先写两句话，写不出就停：

1. 读者是：`<角色>`。例如「我们自己品牌的市场负责人」。
2. 读者看完要决定：`<一个具体动作>`。例如「下一批拍哪三个选题」。

读者不是分析师。报告不证明作者做过多少分析，只帮助读者做决定。

## 第二步：扫术语

把下面两类词标出来，逐个替换。不要加括号解释，直接换成读者的话。

| 不要写 | 改写成 |
|---|---|
| 样本不足 / 样本量偏小 | 条数太少，说明不了问题 |
| 接近下限 | 数量刚够，结论偏弱 |
| 外推 | 推到其他人群；本轮不做 |
| 显著 / p 值 / 置信区间 | 差异有多大；会不会只是偶然 |
| 归因 | 原因 |
| 口径 | 统计范围 |
| 结构化 / 赋能 / 抓手 / 闭环 / 沉淀 | 具体动作，例如「把三类数据放在一张表里」 |
| 建议关注 | 建议做 X，因为 Y |
| 维度 / 层面 | 直接说哪一项 |
| 颗粒度 | 细到什么程度 |

规则：

- 一处术语只能换一次。同一段里反复出现同一个术语，说明这段没想清楚。
- 不要在术语后面加括号注释。读者不会读括号。
- 英文缩写第一次出现必须给中文全称。给不出就删掉。

## 第三步：查数字

每个数字必须能回答四个问题：

1. 数值是多少。
2. 单位是什么。
3. 统计范围是什么（哪个平台、哪段时间、多少条）。
4. 来源是什么（run_id、dataset_id、文件名、查询日期）。

做不到就删掉这个数字。禁止：

- 孤立百分比。例如「67% 的用户不满意」没有分母。
- 不同日期或不同定义的数字相加、平均。
- 把「记录数」写成「用户数」。
- 把「关键词命中」写成「人群占比」。

## 第四步：核证据等级

每条结论标一个等级，用读者能懂的话写：

| 等级 | 给读者的话 |
|---|---|
| Confirmed | 已确认：数据直接支持 |
| Directional | 方向性：数据指向这个方向，但还不够稳 |
| Evidence gap | 证据不足：现在不能下结论 |
| Blocked | 无法判断：缺少授权或数据 |
| Not authorized | 不允许分析：超出授权范围 |

禁止把 Directional 写成 Confirmed。禁止用「显著」「明显」掩盖证据不足。

## 第五步：查禁写结论

VOC 报告先跑整条校验链：

```bash
cd voc_pipeline
bash run.sh <run-id>          # 例如 run-20261029
# 或只跑校验：
python3 -m voc.cli validate --run <run-id>
```

禁写清单以 `voc_pipeline/spec/forbidden_conclusions.json` 为准（当前 12 条）。命中即停，不要发布。

非 VOC 报告，人工检查三类：

1. 用情绪占比代表整体人群。
2. 用饼图或百分比构成表示多标签数据。
3. 用 NPS、CSAT、满意度评分等量表分数。

## 第六步：给决定

每一节最后写一句「所以你要做什么」。写不出，说明这节只是描述，不是洞察。

报告首屏必须包含：

1. 一句话结论。
2. 三个可执行动作。
3. 每条动作的证据等级。

## 第七步：视觉与可读性

- 正文对比度至少 4.5:1，大字至少 3:1。
- 不只靠颜色区分正负，配文字或图形。
- 图表有标题、单位、来源、统计范围。
- 打印时黑白也能读。
- 移动端 390px 宽不横向滚动。

## 输出格式

审阅结论只写三块：

```text
结论：PASS / PASS_WITH_EDITS / FAIL

必须改：
1. <位置>：<问题> -> <改成什么>

可以不改：
1. <位置>：<问题> -> <建议>
```

## 验收

- 业务方能在 30 秒内说出「这份报告要我做什么」。
- 全文没有未替换的术语。
- 每个数字都有单位、范围、日期、来源。
- 没有高于证据等级的结论。
- 禁写清单零命中。
