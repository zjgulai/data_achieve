## 1. TikHub 深度调研与能力差距

### 1.1 TikHub 的产品结构

TikHub 已从单一社交数据 API 扩展为以下组合：

- 统一 API 市场；
- 单一余额和逐端点按次计费；
- 每日阶梯折扣；
- 独立 RPS 套餐；
- 带状态、scope 和有效期的 API Key；
- Swagger、ReDoc、LLM 文档和 SDK；
- 按平台拆分的托管 MCP；
- 数据集市场；
- Chrome 扩展、下载器和演示工具；
- 企业定制与私有部署。

控制台公开路由还显示以下功能：

- API Marketplace 和端点详情；
- 成本计算器；
- API Key 管理；
- RPS 设置；
- 最近 90 天使用日志和 CSV/JSON 导出；
- 数据集购买与刷新；
- MCP 配置生成器；
- 订单、充值、支持工单和企业入口。

### 1.2 值得借鉴的机制

| TikHub 机制 | 对 DIH 的价值 |
|---|---|
| 统一 API Key 生命周期 | 简化 Agent 和外部系统接入 |
| 逐端点价格与成本计算 | 让执行前预算可解释 |
| 配额与 RPS | 防滥用并控制并发 |
| 请求日志 | 支持排障、成本归因和客户用量解释 |
| OpenAPI 生成链 | 让契约、SDK、文档和工具定义同源 |
| MCP 配置生成 | 降低客户端配置成本 |
| 数据集包装 | 借鉴格式、字段预览和刷新产品形态；版本、schema 与哈希由 DIH 自行定义和验证 |
| 面向 Agent 的文档 | 提供 `llms.txt`、逐端点 Markdown 和 Skill |

### 1.3 不应复制的问题

| 问题 | 对 DIH 的启示 |
|---|---|
| `990+`、1,007、1,048、1,050 等数字并存 | 目录、SDK、MCP 和营销必须由同一契约生成 |
| 单个平台拥有数百个 MCP 工具 | 不把端点一对一暴露给 Agent |
| 主要返回平台原始结构 | 客户层必须使用稳定业务合同和归一化数据 |
| 错误 schema 未完整进入 OpenAPI | 客户错误码和恢复方式必须属于契约 |
| 同步调用为主 | 长任务需要持久队列、取消、恢复和不可变回执 |
| 欧洲 TikTok Shop 商品 API 覆盖不足 | 欧洲采用多源矩阵，不能只依赖 TikHub |
| SDK 和服务规格不同步 | 发布前必须做覆盖率和契约漂移检查 |
| 状态页和产品口径不稳定 | DIH 必须以本地探测和运行证据为准 |
| 转售和再分发范围不清 | 上游书面许可必须作为商业 Go/No-Go |

### 1.4 DIH 的相对优势与差距

DIH 已有以下能力，适合建立任务平台而不是 API 镜像：

- 70 个平台和多 provider 供给；
- 统一工具目录和 `catalog_digest`；
- 工作区、项目和成员基础；
- `runs`、`run_steps`、持久队列和租约；
- `run_ledger_entries`；
- `run_evidence_grades`；
- 数据集、版本、漂移和导出；
- 原始记录、内容哈希和证据对象；
- 平台 Skill、Playbook 和控制台；
- TikHub、Apify、Exa 等多源能力。

当前主要缺口：

- 项目 API Key 的 allowlist、日额度和工作区绑定未形成完整客户链；
- 客户 MCP 尚未收敛为稳定高层工具；
- 价格簿未接入 estimate、reserve 和 settle；
- 授权和预算缺少产品入口；
- 新旧运行链路未完全收敛；
- Claim、不可变报告合同和完整交付包未建立；
- 统一审计、保留、删除证明和 DSR 未建立；
- 企业采购材料和上游商业许可未完成。

### 1.5 战略结论

DIH 不与 TikHub 比端点数量。产品差异化是：

> 将多源数据访问转化为带预算、证据、人工审核、不可变交付和验收责任的任务包。

TikHub、Apify 和其他 provider 是内部供给，不是客户产品层。

## 2. 产品定位与路线

### 2.1 路线 H

采用“最小可售闭环 + 平台内核门禁”：

- 商业范围采用最小切片：一个模板、两个包型（Quick 与 Standard）、3–5 家付费设计伙伴；
- 身份、预算、执行、证据、交付和删除作为首单门禁；
- provider 抽象先以进程内适配层落地；
- 不先建设完整 API 市场或独立 provider gateway 服务；
- 不允许试点通过人工旁路绕过平台内核。

### 2.2 产品定义

首期产品是：

> TikTok Shop 母婴新品进入决策任务包。

客户：

- 跨境品牌；
- 为终端品牌提供研究服务的 Agency。

客户购买单位是受治理任务包。数据集和报告是任务包的交付组成，也可以作为任务包的增值项加购；不得脱离任务包把裸数据或单独报告作为主售单位。

### 2.3 Agency 模式

- 一个 Agency 一个工作区；
- 一个终端品牌一个项目；
- Agency 是直接客户，不提供白标门户；
- Agency 的 owner 和 admin 可以管理其工作区；
- member 只能访问被授权项目；
- 项目之间不共享数据、证据、提示词、嵌入或预算；
- 终端品牌如需直接登录，另签合同或另建工作区；
- Agency 对终端客户承担合同和数据使用责任。

### 2.4 正式市场

| 层级 | 市场 |
|---|---|
| core | US、GB、DE、FR、IT、ES |
| supported | IE、NL、BE、AT、PL |

正式支持的定义是：签约前逐市场建立并复核语言、币种、来源矩阵、质量门槛和披露规则。未取得所需书面证据前，该市场不对外列为正式支持，也不承诺交付。正式支持仍不表示每个市场都保证达到最高证据等级。

每个市场必须独立采样、独立判定。不得用美国样本补偿欧洲市场的数据缺口。

### 2.5 首期非目标

【不做】：

- 裸 API 和原始 JSON 转售；
- TikHub 全量端点镜像；
- 公开 API 市场；
- 自助钱包、充值和按调用计费；
- 客户 Cookie 和 Seller Center 登录态；
- Agency 白标和多级分销；
- 因果归因；
- 医疗、安全、法律和召回结论；
- 母婴以外标准模板；
- 11 个市场以外的正式支持；
- 99.9% 可用性承诺；
- 多区域高可用承诺。

【延期】：

- 独立 provider gateway 服务；
- Webhook；
- 周度自动刷新；
- 多区域部署；
- 更多品类与模板；
- 自助入驻和伙伴门户。

## 3. 系统架构与事实源

### 3.1 三层架构

```text
客户 / Agent / 控制台
        │ MCP · 只读 REST · 控制台
        ▼
┌─────────────────────────────────────────────┐
│ 客户产品层：受治理任务平台                  │
│ 任务包 · 报价 · 订单 · 审批 · 报告 · 交付  │
└─────────────────────────────────────────────┘
        │ 不可变计划与统一应用服务
        ▼
┌─────────────────────────────────────────────┐
│ 平台内核层                                  │
│ 目录 · Runs · Queue · Budget · Evidence     │
│ Claims · Datasets · Audit                   │
└─────────────────────────────────────────────┘
        │ 受治理调用；上游细节不出本层
        ▼
┌─────────────────────────────────────────────┐
│ Provider 适配层：内部基础设施               │
│ TikHub · Apify · 公开页面 · 搜索 · 品牌站   │
└─────────────────────────────────────────────┘
```

规则：

1. 客户购买任务结果，不购买 provider 调用。
2. 客户不能选择 provider、端点、分页、重试或降级链。
3. REST、MCP 和控制台调用同一应用服务，不复制业务逻辑。
4. 逻辑分层不要求首期拆成独立服务。
5. 旧同步入口不得绕过身份、预算、证据和审计门禁。

### 3.2 唯一事实源

| 事实 | 唯一事实源 |
|---|---|
| 内部工具目录 | 版本化工具目录与 `catalog_digest` |
| 客户订单 | `workbench_tasks`（七槽位任务单；【需补】） |
| 执行计划 | `workflow_versions`（`workflow_plans` 的不可变计划版本；【现有，需扩展】） |
| 运行状态 | `runs` |
| 步骤执行与单次调用 | `run_steps` 与 `task_runs` 的 1─1 记录及调用回执 |
| 实际金额 | `run_ledger_entries` |
| 证据等级 | `run_evidence_grades` |
| 数据缺口 | 结构化 gap；独立 gap 表或新字段实施前须升级冻结契约 |
| 结论 | `claims` 与 `claim_evidence`（【需补】） |
| 报告内容 | `report_artifacts.contract_json` 中的不可变 `report_contract`（【需补】） |
| 交付事实 | `report_artifacts` 关联的 `delivery_manifest.json`；独立交付账本实施前须升级冻结契约 |
| 身份 | 工作区、项目成员和项目密钥 |
| 审核 | `report_audit_events` 的审核事件；独立审核表实施前须升级冻结契约 |
| 审计 | 追加式统一审计事件；独立统一审计表实施前须升级冻结契约，迁移期聚合现有局部审计 |

其他位置只能保存带源版本的投影或快照，不能反向覆盖事实源。

### 3.3 订单展开

```text
订单
  └─ 不可变计划版本
       ├─ 主市场 Run
       │    ├─ 商品 Step
       │    ├─ 评论 Step
       │    ├─ 达人内容 Step
       │    ├─ 广告增强 Step
       │    └─ 趋势增强 Step
       └─ 对比市场 Run × 0..3
```

执行规则：

- 每个市场一个 run；
- 市场门禁为 `blocked` 时仍保留对应 run 和 gap，不能静默删除；`blocked` 不写入 `runs.status`；
- 核心域是商品、评论和达人内容；
- 广告和趋势属于增强域；
- 一个 step 只能关联一条最终 `task_runs` 记录；如需保存多次 attempt，必须先在冻结契约中登记专用 attempt 结构，或将每次 attempt 建为独立 step；
- 不同来源使用不同 step 表达；
- 订单状态由各市场 run 聚合；
- Quick 与 Standard 共用同一执行内核。

### 3.4 端到端数据流

```text
身份解析
→ 能力发现
→ 成本估算
→ 幂等创建订单
→ 逐市场准入与预算预留
→ 创建 Run
→ 队列领取与租约
→ Step 执行、重试与取消
→ 规范化、伪名化与数据集版本
→ 证据等级与 Gap
→ Claim 草稿与人工审核
→ 不可变报告合同
→ 交付包与验收
→ 新版本刷新
```

任何阶段缺失、过期或不支持时，必须显式记录结构化缺口。`blocked` 只能用于门禁、Claim 或数据域状态；`unknown` 只用于健康状态；gap 保存到结构化缺口对象。不得把这些值写入与冻结契约不兼容的运行状态，也不得猜测、补数或静默降级。

### 3.5 失败语义

| 失败 | 系统处理 | 客户结果 |
|---|---|---|
| 身份无效或密钥撤销 | 立即拒绝，不重试 | 明确认证错误 |
| 白名单外能力 | 拒绝执行 | `tool_not_allowed` |
| 日额度不足 | 拒绝执行 | `quota_exceeded` |
| 预算不足 | 暂停相关范围 | `approval_required` |
| 工具不可执行 | 不分派 | `tool_not_executable` |
| 工具没有价格 | 不报价、不执行 | `tool_not_priced` |
| 市场不支持 | 写 blocked gate 和 gap | `market_unsupported` |
| 瞬态上游错误 | 有界重试 | 重试耗尽后显示缺口 |
| 非瞬态上游错误 | 不重试 | 明确错误和影响范围 |
| 部分来源失败 | 降低证据等级 | 交付部分结果和缺口 |
| 样本不足 | 不生成确定性 Claim | `insufficient_evidence` |
| 报告合同校验失败 | 不发布 | 保留上一正式版本 |
| 校验和不一致 | 禁止下载 | 进入重新生成流程 |
| 刷新失败 | 保留旧版本并标 `stale` | 不覆盖旧结果 |
| 删除或过期 | 保存 tombstone 和审计 | 显示删除范围和剩余事实 |

## 4. 任务包合同

### 4.1 输入合同

| 输入 | 规则 |
|---|---|
| 工作区与项目 | 由会话或项目密钥解析，请求不能覆盖 |
| 模板 | 首期只允许母婴新品进入模板的冻结版本 |
| 品类 | 必须来自母婴二级品类表 |
| 主市场 | 必须选择 1 个正式市场 |
| 对比市场 | Quick 0–1 个；Standard 0–3 个 |
| 时间窗 | 固定起止日期，不能包含未来日期 |
| 决策问题 | 必须可以明确回答 |
| 不回答清单 | 可选；缺省使用通用禁止输出清单 |
| 种子商品或竞品 | 可选；使用时 3–10 个公开链接或平台 ID |
| 目标价格带 | 可选，使用市场原币 |
| 数据域 | 商品、评论、达人内容为核心；广告、趋势为增强 |
| 预算 | `max_cost_usd`、`max_pages`、`max_records` |
| 语言 | 中文主报告、英文执行摘要 |
| 币种 | 原币和 USD |
| 验收联系人 | owner 或 admin |
| 幂等键 | 必填；相同键和相同参数返回原订单 |

客户不能指定 provider、上游端点、分页、重试、降级链、Cookie 或 Seller Center 登录态。

冻结后的变更规则：

| 变更 | 分类 | 审批 |
|---|---|---|
| 增加对比市场、增强域、竞品、种子商品或预算 | 加购 | 预授权内自动；超出额度由 owner 或 admin 批准 |
| 更换主市场、品类、时间窗、样本档位或决策问题 | 新订单 | 重新报价和批准 |
| 增加正式市场 | 新订单 | 重新报价和批准 |

超出额度时只暂停新增范围，未批准时原范围继续执行。

### 4.2 Quick 与 Standard

| 项目 | Quick | Standard |
|---|---|---|
| 市场 | 1 主，可选 1 对比 | 1 主，最多 3 对比 |
| 每市场商品 | 20–50 | 100–300 |
| 每市场评论 | 300–1,000 | 2,000–5,000 |
| 每市场达人内容 | 50–100 | 200–500 |
| 核心域 | 商品、评论、达人内容 3/3 | 商品、评论、达人内容 3/3 |
| 增强域 | 广告、趋势可选 | 广告、趋势可选 |
| 首次输出 | 2 小时方向性快报 | 无机器快报 |
| 正式输出 | 24 小时人工审核版 | 24 小时人工审核版 |
| 证据上限 | L3，不允许 `confirmed` | 达标允许 L4 与 `confirmed` |
| 市场结论 | Quick 方向性标签 | 市场—品类四态 |
| SKU | 只给待验证方向 | 3–5 个有限排序候选 |
| 刷新 | 一次性快照 | 一次性、月度；高级周度刷新只作受限验证，自动化延期 |
| 验收起点 | 24 小时正式版 | 24 小时正式版 |

样本范围按每个市场计算，不能按整包合计。

合同分别记录：

- `floor_n`：最低门槛；
- `target_n`：计划目标；
- `plan_cap_n`：预算和采集上限。

验收只检查 `floor_n`。未采满 `plan_cap_n` 不构成违约。

Quick 的 2 小时稿：

- 标记“方向性、未审核”；
- 不触发验收；
- 不允许最终四态或 `confirmed`；
- 24 小时正式版仍受 L3 上限约束；
- 24 小时正式版可以继续完成原计划内尚未完成的采集步骤，但不得扩大冻结范围；
- 两个版本属于同一任务，不重复收费。

## 5. 质量、证据与 Claim

### 5.1 逐市场质量门槛

| 门槛 | 要求 |
|---|---:|
| 核心域 | 商品、评论、达人内容达到 3/3 |
| 商品 | Quick ≥20；Standard ≥100 |
| 评论 | Quick ≥300；Standard ≥2,000 |
| 达人内容 | Quick ≥50；Standard ≥200 |
| 核心字段完整率 | ≥80% |
| 重复率 | <2% |
| 来源 URL 覆盖率 | 100% |
| 关键 Claim 证据绑定率 | 100% |
| 关键判断独立来源 | ≥2 个 |
| 正式报告审核 | 100% |
| 报告合同和产物校验 | 100% |

分母是去重、市场归属、时间窗和字段校验后的合格记录数，不是 provider 原始返回数。

### 5.2 市场质量状态

| 状态 | 条件 | 允许输出 |
|---|---|---|
| `qualified` | 核心门槛全部通过，无关键缺口 | Standard：完整四态和 SKU 候选；Quick：`worth_validating`、`deprioritize`、`key_risk` 或 `recommend_standard_scope` |
| `qualified_with_gap` | 核心门槛通过，但增强域或关键辅助证据存在缺口 | Standard：`conditional_enter` 或 `insufficient_evidence`；Quick：`recommend_standard_scope`、`key_risk` 或 `evidence_gap` |
| `not_qualified` | 任一核心门槛失败 | Standard：只允许 `insufficient_evidence`；Quick：只允许 `evidence_gap` |

数据域状态：

- `pass`：达到门槛；
- `partial`：有数据，但低于门槛；
- `missing`：没有合格记录；
- `blocked`：市场、权限、配置、条款或上游阻断。

`missing` 不能写成数值 0。`blocked` 不能写成空结果。真实空结果不能解释为“市场没有需求”。

每个缺口必须记录市场、数据域、原因码、实际值、门槛值、对结论的影响、客户可见说明、补救方式和严重度。

### 5.3 证据等级

| 等级 | 含义 | Claim 上限 | 客户显示名 |
|---|---|---|---|
| `L0_unverified` | 只有定义，未验证 | 不生成 Claim | 未验证 |
| `L1_contract` | 契约已校验，未调用 | 不生成 Claim | 契约已校验 |
| `L2_fixture_local` | 本地夹具或离线回放 | `hypothesis` | 本地夹具 |
| `L3_live_single` | 真实调用，但门槛未全部满足 | `directional` | 单次真实调用 |
| `L4_authorized_live` | 真实调用、内部审批有效，且样本、时间窗和独立来源达标 | `confirmed` | L4 · 真实调用达标 |

`L4_authorized_live` 只表示内部执行批准和数据门槛达标。它不表示 TikTok、TikHub 或其他平台授权，不表示法律许可、官方认证、隐私合规认证或转售权。

TikHub 书面许可是独立商业门禁：

- 没有书面许可时，不向客户交付 TikHub 派生结果；
- 取得书面许可不会自动提升证据等级；
- 达到 L4 也不证明已取得商业许可。

### 5.4 独立来源

独立来源按原始记录簇计算，不按端点数量计算。

以下情况只能算一个来源：

- 同一 provider 的不同端点；
- 同一端点的多次调用；
- 同一页面的多条抓取路径；
- 同一记录的翻译；
- 同一内容的转载；
- 同一记录的不同导出格式；
- 两把不同 API Key。

关键判断少于两个独立原始记录簇时：

- Claim 最高为 `directional`；
- 市场不能输出 `enter` 或 `do_not_enter`；
- 只能输出 `conditional_enter` 或 `insufficient_evidence`。

### 5.5 Claim 状态

| 状态 | 含义 |
|---|---|
| `confirmed` | 达到 L4，并通过人工审核 |
| `directional` | 真实数据提供一致方向，但不足以确认 |
| `hypothesis` | 单源或推断，需要进一步验证 |
| `evidence_gap` | 应有证据缺失 |
| `blocked` | 权利、权限、配置或门禁阻断 |

每条 Claim 必须包含市场、时间窗、中英文文本、状态、证据等级、样本量、支持证据、反证、独立来源数、风险标记和审核状态。实施时必须把这些合同字段映射到冻结契约中的 `claims`、`claim_evidence` 及报告合同；如需新增 `text_en`、风险标记或审核状态等持久列，必须先升级冻结契约。

没有证据的 Claim 不能进入正式报告。

### 5.6 Standard 四态与 SKU

| 状态 | 条件 |
|---|---|
| `enter` | 市场 `qualified`，无关键缺口，核心需求 Claim 达到确认要求，有 3–5 个非暂定候选 |
| `conditional_enter` | 机会存在，但有明确条件需要验证 |
| `do_not_enter` | 市场 `qualified`，至少两个独立来源支持，不能由缺失或失败推导 |
| `insufficient_evidence` | 市场未达标或存在关键缺口 |

`conditional_enter` 必须同时给出测试预算、观察周期、成功阈值和止损线。

Standard 输出 3–5 个有限排序 SKU 或价格带候选。每个候选必须包含目标市场、排名、原币和 USD 价格带、核心属性、需求证据、竞争证据、最低证据等级、风险标记和下一步验证动作。排序表示描述性机会顺序，不表示成功概率。候选少于 3 个时，不得补足虚假候选，也不得输出 `enter`；应改为 `conditional_enter` 或 `insufficient_evidence`。

Quick 不使用四态，只允许：

- `worth_validating`；
- `deprioritize`；
- `key_risk`；
- `evidence_gap`；
- `recommend_standard_scope`。

所有 Quick 标签必须标记为方向性。

### 5.7 描述性归因

允许表达共同出现、相关和描述性差异。不允许表达导致、驱动、提升、降低、造成、证明或其他因果含义。

所有比较必须提供市场、时间窗、样本量、计数类型、证据等级和反证。

不预测销量、市场份额、转化率或营收。

## 6. 报告、交付与验收

### 6.1 不可变报告合同

`report_artifacts.contract_json` 中的不可变 `report_contract` 是正式报告的唯一内容事实源；对外交付时序列化为 `report_contract.json`，至少包含：

- 合同、订单、模板和报告版本；
- 决策问题和不回答项；
- 每个市场的状态、质量、样本、门槛和缺口；
- Claims、Evidence 和反证；
- Standard SKU 候选；
- 数据集版本和哈希；
- 质量记分卡；
- 来源权利和上游商业门禁；
- 原币、USD、汇率日期和来源；
- 语言和翻译方法；
- 限制、未知项和非承诺；
- 审核人、审核范围、审核时间、审核版本和合同哈希；
- 验收快照；
- 交付 bundle、manifest、访问范围和保留类别。

规则：

1. 报告合同使用 canonical JSON。
2. 发布前通过 schema、语义和禁用词校验。
3. 发布后不能修改。
4. 修订生成新的 `contract_id` 和 `report_version`。
5. 新版本通过 `supersedes_id` 指向旧版本。
6. 渲染器只读取合同，不重新查库或调用模型。
7. 标题数字不能写死在模板中。
8. 公开投影不包含 provider、端点、凭据、内部单价和内部批准人。
9. 报告首屏必须显示各市场状态、最低证据等级、关键缺口和 Claim 分布。

### 6.2 正式交付包

正式交付包包含：

1. 中文主报告；
2. 英文执行摘要；
3. CSV 或 Parquet 数据集；
4. 数据字典；
5. 逐市场质量记分卡；
6. Claim 到 Evidence 的索引；
7. 客户运行回执；
8. 公开报告合同；
9. 限制、未知项和 Gap；
10. `delivery_manifest.json`；
11. 交付时验收快照。

每个文件必须有 SHA-256。manifest 自身哈希存放到外部 sidecar 和追加式交付审计事件，避免自引用。若实施独立交付账本或验收账本，必须先升级冻结契约。

发布后的交付包不可修改。验收状态变化写入追加式验收事件，不能修改 manifest。

### 6.3 人工审核

黄金期：每个模板前 5 份正式报告，或前 3 个设计伙伴的全部正式报告，取覆盖更多者，逐条审核。

稳定期：

- 所有进入结论必审；
- 所有标题数字必审；
- 所有跨市场比较必审；
- 所有风险 Claim 必审；
- 其余证据抽检 20%–30%；
- 抽检失败时整份报告回退全审。

Quick 的 2 小时稿不审核。Quick 的 24 小时正式版和 Standard 正式版必须审核。无审核签字不能发布正式报告。

医疗、健康、安全、法律或召回结论不属于首期交付范围。报告如为说明限制而引用相关内容，或涉及儿童/未成年人风险提示，必须由第二人复核，不能标记为 `confirmed`，也不能构成医疗、安全、法律或召回判断。审核后如修改 Claim、数字或证据，原签字失效，必须重新审核。

### 6.4 验收与补救

- 5 个工作日从正式版交付时开始计算；
- Quick 的 2 小时稿不触发验收；
- 客户需引用验收清单具体项目提出异议；
- 逾期未提出异议，视为验收；
- Agency 终端客户意见属于修订意见，不能直接触发拒收；
- 事实错误不受验收期限制。

| 情形 | 处理 |
|---|---|
| 事实、计算或证据引用错误 | 免费纠正，不限次数；生成新版本并重新审核 |
| 同范围表达、图表和重点调整 | 包含一轮 |
| 新增市场、品类、竞品、时间窗或数据域 | 新订单或加购 |
| 平台执行缺陷导致门禁失败 | 免费补证或重跑一次 |
| 第二次仍失败 | 按未交付部分退款或抵扣 |
| 客户中途取消 | 按已完成阶段结算 |
| 真实空结果 | 不自动退款，但披露来源、尝试次数和边界 |
| `insufficient_evidence` | 有效交付结果，不自动触发免费重跑 |

免费重跑只适用于平台可以控制的执行缺陷：临时上游失败、平台配置遗漏、流水线造成字段完整率不足、去重故障、报告合同校验失败和校验和错误。以下情况不自动触发免费重跑：市场不在支持目录、上游商业权利未确认、真实空结果、客户输入错误、客户未提供约定授权，以及数据本身不足以支持判断。

退款或抵扣按合同预先冻结的“市场 × 数据域”权重计算，不能在争议发生后临时分配权重。

### 6.5 刷新与可比性

每次刷新生成新计划版本、runs、数据集版本、Claims、报告合同、交付包和验收周期。旧版本保持不可变。

刷新失败时，保留上一个可用交付包并标记 `stale`，列出未刷新的市场和数据域；不允许部分结果覆盖旧正式版本。

只有模板版本、市场及主市场/对比市场角色、时间窗长度和对齐方式、指标定义、计数类型、分类和编码本、汇率政策、伪名盐值和来源组合兼容，或已明确披露等价替换时，才能计算跨期变化。

刷新可比状态：

- `comparable`；
- `comparable_with_caveats`；
- `not_comparable`；
- `failed`。

来源变化不能被平滑成连续趋势。必要时建立新基线。

## 7. 身份、预算、隐私与运营治理

### 7.1 客户角色

客户角色固定为 `owner`、`admin`、`member`：

| 动作 | owner | admin | member |
|---|---:|---:|---:|
| 查看被授权项目的任务和交付 | 是 | 是 | 是 |
| 在预算内创建或取消任务 | 是 | 是 | 是 |
| 管理项目密钥 | 是 | 是 | 否 |
| 修改密钥白名单和日额度 | 是 | 是 | 否 |
| 批准超额和加购 | 是 | 是 | 否 |
| 调整项目预算 | 是 | 可发起申请 | 否 |
| 管理成员 | 是 | 可发起申请 | 否 |
| 删除项目或关闭工作区 | 是 | 可发起申请 | 否 |
| 查看工作区审计 | 是 | 是 | 仅本人活动 |
| 确认 DPA 和子处理者变更 | 是 | 否 | 否 |

工作区必须至少保留一名 owner。发起人不能批准自己的超额、加购或密钥变更。批准必须来自经过 MFA 验证的人类会话。Agent、项目密钥和服务账号不能批准。内部审核员不进入客户成员列表，也不能成为 owner、admin 或 member。

### 7.2 项目密钥

- 绑定一个工作区和一个项目；
- 包含工具白名单和日额度；
- 明文只显示一次；
- 数据库只存哈希和前缀；
- 每个项目最多一把有效密钥；
- 轮换必须原子完成：撤销旧密钥并签发新密钥，失败时整体回滚；当前实现如不满足，属于【需补】并阻断客户密钥签发；
- 撤销后新请求立即失败；
- 完整密钥不得进入 URL、日志、错误、报告、bundle 或工单。

### 7.3 客户 MCP

客户 MCP 只包含八个稳定工具：

1. `discover_capabilities`
2. `estimate_task`
3. `create_task`
4. `get_task`
5. `cancel_task`
6. `get_delivery_manifest`
7. `get_evidence`
8. `collect`

客户合同中的 `collect` 只允许模板白名单内的稳定 `capability_id`，由服务端选择 provider，并创建受治理的 run 和 step。当前内部 `collect(endpoint_type, project_id, params)` 属于旧接口；如不能保持参数兼容，客户版必须使用新工具名并遵守“只增不改”。

请求检查顺序固定为：Bearer 鉴权 → 密钥状态 → 工作区与项目绑定 → 工具白名单 → 能力白名单 → Cookie 隔离 → 日额度 → 速率与并发 → 预算 → 执行与审计。白名单失败返回 403，日额度或限流失败返回 429，预算不足进入待批准状态。

Agent 可以在白名单和预算内查询能力、估算、创建任务、查询所属项目任务和交付、取消允许取消的任务，以及发起预算内加购；不得批准超额或加购、修改预算、签发/轮换/撤销密钥、修改白名单和日额度、删除项目或数据、请求退款、跨项目/跨工作区访问、调用 provider 原始端点或获取原始凭据和响应。

客户 REST 只读面包括任务包发现、市场和数据域说明、任务状态读取、交付包下载和分享。现有控制台 REST 不自动成为公开开发者合同。

内部端点级工具不能出现在客户 `tools/list`、文档或 SDK 中。客户可访问的工具目录只返回任务模板白名单内的 capability 投影。MCP 工具只增不改；破坏性变化必须使用新工具名，旧工具至少保留一个迁移周期后再下线。任何新工具名和路径实施前必须先登记到冻结契约。

### 7.4 Cookie 隔离

首期客户任务包、客户 MCP 和客户交付链不接受客户 Cookie。

现有依赖 `tiktok.creator_cookie` 项目凭据的内部 TikTok 工具继续保留，但必须：

- 从首期模板白名单移除；
- 从客户 MCP 移除；
- 其输出不能进入客户数据集、Claim、报告和 manifest；
- 保持在授权工作区的内部控制台范围；
- 调用和拒绝均写审计。

### 7.5 冻结账本契约

`run_ledger_entries` 的八列和六种 `entry_kind` 不得改变。

实际成本：

```text
sum_cost = SUM(amount_usd)
           WHERE entry_kind IN ('settle', 'release')
```

剩余额度：

```text
remaining_budget = max_cost_usd - sum_cost
```

符号：

- `settle`：正数实际成本；
- `release`：负数，修正已写入的 `settle`；
- `estimate`、`reserve`、`accrued`、`block`：不计入实际成本。

每个 run 使用 `authorizations.max_cost_usd`。订单预算按市场拆成 run 授权，订单级上限等于各市场授权之和。`remaining_budget` 可以为负，不能截断为零。实际成本高于原结算时，追加新的正数 `settle`。单价未知时，不得按零成本执行或报价。预算检查与预留必须原子执行。超出项目总额度时，必须由 owner 调整额度，不能通过单笔审批绕过。人工审核授权和预算授权必须分开记录。

账本只追加。不得修改或删除历史行。退款、抵扣、发票和收入确认属于财务系统，不能写进运行成本账本。

### 7.6 隐私和保留

普通评论者使用工作区级伪名：

- 同一工作区稳定；
- 跨工作区不可关联；
- Agency 作为直接客户时使用其工作区盐；同一 Agency 工作区内的终端品牌项目共享工作区级伪名稳定性，但不得跨项目查询、分析或导出关联结果；不同工作区使用不同盐；
- 项目隔离依靠权限，不改成项目级盐；
- 不提供反查映射。

导出前遮蔽联系方式、个人主页链接、评论正文中的外部链接和普通用户 handle。证据来源 URL 必须保留，必要时仅去掉追踪参数。品牌、店铺和商业创作者的公开身份可以保留。

| 数据 | 保留期 |
|---|---:|
| 原始响应 | 30 天 |
| 标准化数据集 | 12 个月 |
| 正式报告和交付包 | 24 个月 |
| 运行日志 | 180 天 |
| 安全与访问审计 | 24 个月 |
| 备份 | 30 天 |

保留期变更必须经过合同和法务流程。不能由本设计增加“只能延长”或“只能缩短”的规则。数据不得跨客户复用；匿名行业基准只能由客户单独书面 opt-in，并达到足够的聚合客户数量，避免反推出单一客户数据。

删除流程：owner 发起并二次确认，admin 可以发起申请；检查法律保留、合同争议和安全事件；撤销项目密钥和分享链接；删除活跃业务数据或写 tombstone；清理缓存、搜索索引和临时文件；向子处理者发送删除请求并保存回执；备份在 30 天内自然过期；生成删除证明和审计事件。账本、审计、证据等级和审核记录不能因业务数据删除而被硬删，只保留必要的最小元数据，不继续保存已删除正文。

DSR 流程：接收请求 → 核验身份与授权 → 确认 controller/processor 责任 → 在当前工作区内定位数据 → 执行访问、更正、限制或删除 → 通知子处理者 → 生成审计和结案记录。不得跨工作区搜索或使用伪名 ID 关联其他客户数据。具体时限、例外和责任划分由律师确认。

### 7.7 子处理者、跨境和 LLM

子处理者清单必须覆盖实际使用的 TikHub、Apify 及具体 Actor、Exa、Firecrawl、Jina，以及工具目录中实际调用的其他外部 API、云托管、对象存储、LLM、邮件、监控、客服和支付服务。清单应从实际调用链和工具目录生成，不能只依赖手工枚举。新增或替换子处理者应提前 30 天通知客户；异议和终止方式写入 DPA。

TikHub DPA 不等于数据转售授权。首笔付费交付前，必须取得书面确认，覆盖派生交付、Agency 分享、缓存、存储、署名和查询数据的使用方式。

首期不承诺 EU 数据驻留或多区域高可用。DPA 和安全问卷必须披露实际生产、备份、子处理者、内部支持区域和跨境路径。生产 A 和生产 B 不能自动被当作灾备或同一区域；必须先核实两套环境的区域、数据路径、代码、镜像和配置差异。SCC、UK IDTA、DPF、TIA、PIPL 等机制是否适用，由律师确认；未取得书面意见前，不能向对应法域客户作出跨境承诺。

使用 LLM 时：

- 供应商提供零保留和禁止训练的书面条款；
- 只发送伪名化、最小化摘录；
- 不发送完整数据集、联系方式、Cookie、密钥和原始身份；
- 输出只作为草稿；
- 不建立跨客户上下文、提示词复用或嵌入复用；
- 供应商列入子处理者清单；
- 条款不满足时关闭 LLM，不静默切换其他模型。

### 7.8 内部访问与审计

内部人员默认没有常驻客户数据权限。内部访问按以下类型控制：报告审核只访问已分配报告、Claim 和证据；常规支持需要工单和客户批准，范围限于指定项目、只读、限时；工程排障需要事件负责人批准并优先使用日志和元数据；紧急访问需要双人批准、立即告警和最小范围；销售演示使用独立销售工作区，只允许合成数据，不得读取客户工作区。所有访问记录工单、理由、范围、开始和结束时间；紧急访问结束后轮换相关凭据并复盘。

紧急访问不能绕过租户隔离、预算、密钥白名单、删除或法律保留。

审计事件至少覆盖：登录、登出、失败登录和角色变更；密钥签发、轮换、撤销和拒绝；预算调整、超额审批和阻断；订单和 run 的创建、取消、重试和终态；工具调用结果和耗时；导出、下载、分享、访问和撤销；删除请求、删除执行和删除证明；内部审核、支持和紧急访问；子处理者、价格簿、目录和安全配置变化；备份和恢复演练。

审计事件必须：

- 只追加；
- 防止修改和删除；
- 不记录明文密钥、Cookie、盐和原始个人数据；
- 带工作区、项目、主体、请求和结果；
- 形成可验证哈希链；
- 在独立防篡改存储中保存链锚；
- 保留 24 个月；
- 支持客户导出本工作区范围记录。

### 7.9 SLO 和灾备

Quick 2 小时、Quick 24 小时和 Standard 24 小时是交付目标，不是可用性 SLA。

首期不承诺 99.9% 可用性、多区域高可用、固定 RPO 或 RTO。具体 SLO 在试点中校准。

以下是不允许失败的硬控制：

- Claim 证据链接覆盖率为 100%；
- 逐市场质量状态完整率为 100%；
- 跨工作区成功访问为 0；
- 账本不平和重复结算为 0；
- 预算 100% 阻断生效；
- PII 检查失败后发布为 0；
- 客户链出现 `creator_cookie` 为 0；
- 关键操作缺失审计为 0。

对外声称备份保留 30 天前，必须完成数据库和对象存储备份、加密、保留任务、恢复演练、删除重放验证、法律保留恢复和 RPO/RTO 实测。两套生产环境只有在故障域、数据复制、切换和恢复经过验证后，才能称为灾备。

### 7.10 企业采购材料

企业采购材料至少包括 DPA、完整子处理者清单、数据流图、保留和删除政策、安全问卷及证据、跨境传输说明、内部访问和审计说明、事件响应与灾备计划、实际持有的认证/测试/保险证明、TikHub 等上游的书面商业许可，以及 LLM 零保留和禁止训练条款。

### 8.2 PG0

- 合成数据黄金路径端到端通过；
- 一份内部 Quick 和一份内部 Standard 通过端到端验收；

### 8.3 P1 商业试点

目标组合：3 家跨境品牌和 2 家 Agency，同一母婴品类优先。伙伴需要有实际决策人、预算和采购路径；具体市场按其业务需求从正式市场目录选择。

试点规则：

- 3–5 家实际签约并付款；PG0 的书面承诺不计入 P1 实际付费成果；
- Agency 的终端品牌不单独计入设计伙伴数量；Quick-only 免费线索不计入付费伙伴；
- 不新增模板、品类或正式市场；
- 不提供免费定制；
- 不卖裸 API；
- 不按调用次数计费；
- 不接受客户 Cookie；
- 不把产品缺口包装成专业服务；
- 不把 LOI、口头意向或未付款合同计入付费成果；
- Standard 月度刷新可作为付费扩展；
- 周度刷新只作受限验证，不作普遍承诺；
- 证据不足时最多延长一次，最长 30 天，并说明缺少的证据、负责人和复核日期；
- 延长后仍无证据，结论为 No-Go。

### 8.4 PG1 指标

| 类别 | 硬门禁 |
|---|---|
| 商业 | 3–5 家实际付费；至少 3 家活跃；至少 2 家购买第二任务或刷新；回款率 100%；企业采购准入在实际付费伙伴全部完成 |

| 产品 | 正式任务完成率 ≥90%；5 个工作日内完成验收或进入明确异议流程；至少 2 家购买第二个任务或刷新 |
| 质量 | 每个约定市场有质量状态；不合格市场正确输出证据不足；正式 Claim 追溯率 100%；Claim 等级不超过证据上限 100%；关键 Claim 的独立来源判定覆盖率和正确率均为 100%；刷新可比性状态完整 100%；重大口径争议 0 |
| 系统 | 跨工作区泄露 0；客户执行回退演示工作区 0；账本不平 0；重复结算 0；幂等重复计费 0；超预算继续执行 0；关键操作缺少审计 0 |
| 合规 | DPA 和子处理者覆盖 100%；数据源书面权利覆盖 100%；客户链 Cookie 暴露 0；PII 违规发布 0；LLM 处理方式已披露并经客户接受 100% |

预警指标：报价成本与实际成本偏差建立稳定区间并可解释；价格实现率记录成交价与报价差异；一次验收通过率目标 ≥70%；支持首次响应达标率 ≥90%；免费补证或重跑率目标 ≤20%；运行成功率、延迟、队列等待和 provider 错误率建立试点基线。预警阈值和复核人必须在 PG1 评审前书面约定；未约定时不能据此作 Conditional Go。

### 8.5 PG1 结论

| 结论 | 条件 |
|---|---|
| Go | 所有硬门禁通过，商业和单位经济成立；没有未解决的重大安全、隐私、财务或质量事件；没有向裸 API、按次计费或第三方 API 市场发生范围漂移 |
| Conditional Go | 硬门禁全过，仅已约定预警指标未达，且有整改负责人和复核门禁 |
| No-Go | 任一硬门禁失败，或商业模型不成立 |

Conditional Go 不能豁免任何硬门禁。

P2 不在本次批准范围。PG1 通过只允许提出 P2 方案，不自动进入 P2。

### 8.6 停止与回退

| 类型 | 触发条件 | 立即动作 |
|---|---|---|
| 合规停止 | 未授权数据使用、Cookie 进入客户链、平台或监管禁令 | 停止受影响任务和市场，撤销访问，保全证据 |
| 安全停止 | 跨工作区访问、密钥泄露、入侵或未授权导出 | 隔离工作区，轮换密钥，启动事件响应 |
| 财务停止 | 账本不平、重复结算、未授权计费 | 停止新增付费调用，冻结结算并对账 |
| 质量停止 | 伪造 Claim、证据丢失、连续错误结论 | 停止交付，保留证据，发布更正版本 |
| 上游停止 | 上游封禁、停服或条款变化 | 停止受影响市场，验证替代来源 |
| 技术回退 | 发布回归、合同不兼容、数据损坏 | 关闭新功能，暂停队列，回退代码和配置 |

回退不修改历史事实：

- 已发布报告和 bundle 不可变；
- 错误报告发布新版本；
- 账本只追加更正；
- 已完成 run 的终态不回退；
- 重跑创建新 run；
- 单市场问题只停止该市场，系统性问题停止整个任务包；
- 恢复前重新通过对应门禁。
