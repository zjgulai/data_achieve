# DIH 历史 UI/UX 方案与当前计划对照

> 对照日期：2026-10-17
> 历史来源：仓库唯一 checkpoint tree 中恢复出来的 `docs/product/data-intelligence-ui-ux-integrated-plan-2026-07-22.md`（2026-07-22 创建、2026-07-27 更新）。
> 当前来源：`docs/architecture/【技术方案】DIH整站能力整合方案.md`、`【设计规范】DIH首页与目录视觉规范.md`、`【逆向报告】Monid网站UI与能力逆向.md`、`【能力图谱】DIH-控制台能力地图.md`、`【能力总账】DIH-平台能力现状与维护手册.md`，以及 `【交接文档】DIH前端实施交接.md` 和当前代码。
> **用途：** 决策材料，不是实现授权。历史方案的 `approved_for_implementation` 状态只代表 2026-07-22/27 的历史状态，不能代替当前用户对新 IA 或 `apps/web` 去留的决定。

## 执行摘要

1. **可直接保留的产品原则：** 业务语言优先、证据可钻、状态要带原因和下一步、默认/高级诊断分层、禁止虚假可执行按钮、目录以行列表为主、保留暖纸底和玫瑰品牌色。
2. **当前执行基线是 2026-10 方案，不是 7 月方案。** 7 月方案以 `apps/web`、Next.js 15、已有 Planner/Run 生命周期和一份完整 Web IA 为前提；当前实施对象是 `apps/scraper-console`、Next.js 16。旧方案包含多个尚未授权或当前不可用的写入/执行流程。
3. **策略分层已成为前端的硬约束。** 86 个采集器类型中 53 个 `unsupported`；前端只能依据当前接口的可达性字段显示动作，不可把旧方案里的 Run/Activate/Send 草图当作现存能力。
4. **旧方案不能直接丢弃。** 它有现行 10 月文档没有同等细节的交互原则和屏幕级设计。但应作为历史参考，不得把旧 TODO、旧路由或旧授权状态复制进本轮实现。

## 可移植的旧方案设计内容

旧方案不是整份作废。下面这些内容与当前方案不冲突，可作为参考，不要求逐字照搬：

- 每个页面回答「当前上下文、业务结果、原因/证据、可执行动作、动作影响」五问。
- 默认层使用业务语言；Advanced 层才显示 fingerprint、quota、request ID、RawRecord ID 等诊断术语。
- 状态表达公式：状态 + 原因 + 业务影响 + Evidence + 下一步。
- 行动优先级：每个决策区域最多一个 primary action；Gated 与 destructive 动作必须有明确门槛或确认。
- 数据比较用列表/表格优先，不以同构大卡片堆叠。
- 不复制参考品牌，不用纯颜色表达状态，不制造没有后端支撑的假按钮。

## 不能从旧方案推出的授权

旧方案 frontmatter 的 `approved_for_implementation` 是历史状态；它不授权当前会话做以下事项：

- 删/冻结 `apps/web` 或改生产 compose、nginx、CI。
- 改后端 API、鉴权、权限、密钥、数据库 schema 或真实供应商调用。
- 将 fixture / simulated run 变成 live execution。
- 新增 Activate、Run、Send、Export 或付费行为。
- 改整合方案 §4.3 已冻结的路由映射。
- 改 token 单一来源或合并组件词表——这些仍等当前产品决策。
