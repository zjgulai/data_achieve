### 0.5 倒推的边界

1. PRD 与 Playbook 定义“要交付什么”，不证明“现在有什么”。实现判断以文件和测试为准。
2. UI 设计的 11 条路由可以倒推，但三个阻断项必须先解除：`tool_catalog` 缺失、真实运行层未挂载、`report_contract` 不存在。对应 B1、B3、B4。
3. 工作流设计的 TaskRun 是 `automation_runs`，不是现有 `task_runs`。前者是一次任务执行，后者是一次采集调用。两者不得混用。
4. 模块设计的 P0-P12 顺序可执行，但它没有计入 main 已有的 `tool_catalog` P0 包。本计划把这 4 个提交并入 B1，避免重复实现。

## 1. 结论

下一批只做“基线收敛 + 目录单一事实源”。用两周完成 PRD 的 M0 与 M1 前半：先把 main 的 4 个 tool_catalog P0 提交合入，再把工作树 133 个改动按运行核心、TikTok R1、控制台、文档四组代码/文档提交，另做一次根目录清理；把已全绿的测试设为回归守卫（基线=空集）；把写接口从 demo workspace 回退改为 fail-closed；用 286/258（HEAD）、303/275（工作树）、284 条映射对账，生成 `tool_catalog` 表与统一摘要；让 REST、MCP、脚本三处返回同一个 `catalog_digest`。下一批不做 `claims`、`report_contract`、`/workbench`、11 条路由重写、`workflow_execution` 复活、T4 与 TikTok R1 迁移应用。理由：这些工作的上游输入都依赖 `tool_catalog`；在目录数字不一致、鉴权可回退、执行层是 fixture 的情况下做界面或报告，只会把错误固化。

| 做 | 不做 |
| --- | --- |
| 提交已部署但未入库的运行核心 | 不新增采集器 |
| 建立回归守卫（基线=空集） | 不重跑已修好的测试 |
| 写接口 fail-closed | 不改读接口的全部鉴权 |
| `tool_catalog` 表与三处对账 | 不建 `claims` 与报告合同 |
| 策略感知的 executable 计数 | 不重写报告渲染器 |
| 幂等唯一约束 | 不复活 fixture 执行栈 |

### 2.1 B1 说明

B1 是唯一立即开工的批次。它不产生用户可见功能。它的产出是后续所有统计、执行、报告的可信前提。

B1 结束时必须能回答四个问题：

1. 当前到底有多少个可发现工具？答案来自 `tool_catalog` 的摘要，不来自三处硬编码。
2. 哪些工具可执行？答案由 `outbound_policy` 决定，不由 availability 猜测。
3. 谁在调用？答案来自登录用户，不来自 demo workspace。
4. 本次改动是否引入新失败？答案来自基线守卫，不来自人工判断。

### 2.2 B2 说明

B2 只做授权与等级，不做执行。授权包括两件事：域名 grant 与项目级密钥。等级只做纯函数与阈值表，不写 run。

B2 结束时，planner preview 至少有一个真实工具从 `held` 变为可选。否则说明 tool_catalog 投影没有接通，B3 不得开始。

### 2.3 B3 说明

B3 新建执行层。执行层包装 `execute_collection_task`，不重写采集内核。B3 同时修调度器的两个已知缺陷：租约不续期、异步任务用进程内 `BackgroundTasks`。

B3 不接 UI。回执先用 API 与集成测试验收。

### 2.4 B4 说明

B4 才允许出现 `claims` 与 `report_contract`。这两个表必须由 B3 的 run 与 B2 的等级提供输入。B4 的渲染器是纯函数，不得读库、联网或调用 LLM。

### 2.5 B5 说明

B5 才改前端主路径。范围是 11 条路由中的授权区与目录、报告阅读页。公开区首页与文档页可以延后。`/settings/account` 死页已在 B1 删除。

### 2.6 B6 说明

B6 是条件批次。只有决策 D3 选择“应用迁移”时才启动。未应用迁移时，T4 必须保持延期，不得用原始记录冒充 canonical 数据。
