## 1. 表名

### 1.0 语义边界（最高优先级）

`runs` 与 `run_steps` 的语义此前在架构与模块设计之间冲突。
现冻结如下，两份文档必须服从。

| 表 | 语义 | 粒度 | 不承担 |
|---|---|---|---|
| `workbench_tasks` | 七槽位任务单 | 一次业务问题 | 不记录执行状态 |
| `workflow_plans` / `workflow_versions` | 计划单与版本（复用现有表） | 一个任务可有多版计划 | 不记录执行 |
| `runs` | 一次执行运行 | 一份计划执行一次 | 不存七槽位 |
| `run_steps` | 一次执行中的一个步骤 | 一次工具调用 | 不存计划正文 |
| `task_runs` | 单次采集执行的记录（现有表） | 一个 collector 调用 | 不存编排 |

关系：

```text
workbench_tasks 1─n workflow_versions 1─n runs 1─n run_steps 1─1 task_runs
```

结论：

- **`runs` 是执行运行，不是任务单。**
- **`run_steps` 是执行步骤，不是计划单。**
- 七槽位存 `workbench_tasks`。
- 计划正文存 `workflow_plans` 与 `workflow_versions`（复用现有表，不新建）。

### 1.4 身份事实源

`workspace_members.role` 是唯一授权事实源。取值只有 `owner`、`admin`、`member`。

`workspaces.owner_id` 不是授权事实源。它只表示创建者与账单联系人。每个工作区的 `owner_id` 用户必须有一条 `workspace_members.role='owner'` 行。该用户不得被降级或移除，直到所有旧检查迁移完毕。

`project_members` 只表达 `member` 可查看某项目。owner/admin 不依赖该表即可访问工作区全部项目。`project_members` 不设项目级角色列。

每个工作区至少有一名 owner。最后一个 owner 不能被降级或移除。

功能开关 `WORKSPACE_RBAC_ENFORCED` 控制项目 ACL 是否生效。关闭时保留旧的项目可见性；打开时执行本节的 403/404 规则。审计写入没有关闭开关。

`audit_events.prev_hash` 指向同工作区上一事件的 `event_hash`，字段含义是“上一事件哈希”。首条事件的 `prev_hash` 是 64 个 `0`。`event_hash` 是 SHA-256 小写十六进制。

## 2. 枚举

### 2.1 运行状态 `runs.status`

```text
queued · running · completed · failed · cancelled
```

`workflow_plans.status` 是另一套枚举。它允许 `held`。
`held` 表示计划待人工处理，不是运行态。

**不得出现 `degraded`。**
Playbook §1.4 规定健康度与运行结果分离。
`degraded` 只用于 `health_status`。

**不得出现 `held`。**
`held` 是 fixture 运行表的历史取值，属于 `workflow_runs`，不属于 `runs`。

### 2.2 步骤状态 `run_steps.status`

```text
pending · running · success · empty · config_gated · failed · skipped
```

### 2.3 运行结果 `run_steps.outcome`

运行级聚合结果写在 `runs.outcome`。
单步结果写在 `run_steps.outcome`。
两处取值相同。

只有四值。与 Playbook §1.4 一致。

```text
success · empty · config_gated · failed
```

**不得出现 `partial`。**
部分成功用 `status=success` 加 `outcome=success` 加 `records_count > 0` 表达。
若确实需要第五态，必须先改 Playbook。

### 2.4 健康度 `health_status`

```text
healthy · stable · degraded · outage · unknown
```

只存在于 `tool_catalog` 与运行证据视图。
不写入 `runs` 或 `run_steps`。

### 2.5 证据等级

```text
L0_unverified · L1_contract · L2_fixture_local · L3_live_single · L4_authorized_live
```

`ToolContract.max_evidence_grade` 是工具上限。
`RunEvidenceGrade.grade` 是本次运行的结果。
`task_runs.evidence_grade` 与 `runs.evidence_grade` 是该结果在两个表上的镜像。

字段名规则：

- 工具上限：只叫 `max_evidence_grade`。
- 本次结果：叫 `grade`（在 `run_evidence_grades` 表内）或 `evidence_grade`（在 `runs`、`task_runs` 表内）。
- **禁止** `evidence_grade_cap`。工具上限不是 cap，是 max。

### 2.6 claim 状态

```text
confirmed · directional · hypothesis · evidence_gap · blocked
```

显示别名（Verified / Supported 等）只用于界面文案，不得写进合同。

### 2.7 门禁状态

```text
pending · pass · fail · blocked · expired
```

门禁状态存在 `authorizations.gate_status`。
不另建门禁表。不建 `automation_gate_evaluations`。

`expired` 用于授权过期导致的门禁失效。
UI 必须为它提供状态与文案。

### 2.10 审计动作注册表

审计动作只有一个版本化注册表：`audit-actions.v1`。注册表同时存在于本节与附录 A 的 `audit_actions` 对象，两者必须逐字一致。所有动作只写入唯一的 `audit_events` 表；不得建第二张审计表。`services.audit_log.AUDIT_ACTIONS` 必须与注册表动作名逐字一致。

规则：

1. 每个动作只有一个写入 owner；owner 切片负责在实现中调用 `append_audit_event`。`run.created` 的 owner 是 C4，唯一写入入口是 C4 `services/run_creation.create_run_with_audit`；C6 旧入口收敛只调用该接缝，不直接写 `run.created`。
2. 下游切片不得自造动作名。未登记动作抛 `audit_action_unregistered`（HTTP 500）；动作名形状非法抛 `audit_action_invalid`。
3. 动作名只允许小写字母、数字、下划线与点，至少两段，最长 80 字符。
4. 已登记的名称不得改名。新增动作必须先改本节与附录 A，再升级注册表版本；不得只改代码。
5. `reviewer.*` 动作只由 C2 与 C9 写入。内部审阅者不是客户工作区角色；`workspace_members.role` 仍然只有 `owner`、`admin`、`member`，不得出现 `reviewer`。
6. `audit_events.action` 是 `string(80)`，数据库不建 Enum；本注册表是服务层与文档层的唯一校验源。
