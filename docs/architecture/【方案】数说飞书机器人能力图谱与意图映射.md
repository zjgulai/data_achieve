### 1.2 状态定义

- **verified**：最近一次实测成功，且 `last_records_count ≥ 1`。
- **缺配置**：`missing_configuration` 非空。当前快照中这 21 个端点同时带 `policy_block_reason`；补配置后仍需策略复核。
- **纯策略受限**：`policy_block_reason` 非空，且 `missing_configuration` 为空。原因是 `UNSUPPORTED_COLLECTORS`；请求参数不能解锁。
- **degraded**：最近一次实测失败。包括上游 4xx、Apify Actor run FAILED、运行前 403、超时。
- **empty**：实测成功但返回 0 条。
- **disabled**：catalog 标记下线，不提供调用。

> 关键口径：verified 只表示“端点可执行且最近有数据”，不表示字段完整、分页稳定、返回 schema 已验收。多个 verified 端点最近只有 1 条记录。机器人编排前应按 `capability_id` 抽样验证。

### 3.6 意图路由规则

1. 显式命令优先。用户输入 `采集`、`详情`、`能力`、`平台`、`总览`、`帮助` 时，走命令层，不进入自由文本解析。
2. URL 优先按平台识别。视频 URL 进入字幕/评论意图；普通网页 URL 进入 `generic_web` 或 `exa_contents`；GitHub URL 进入 `github_repo`。
3. 平台 + 动词 + 关键词进入社媒搜索。平台词决定端点族，动词决定意图，关键词写入 `keyword` 或 `searchTerms`。
4. 账号 handle 或公司名进入画像/发帖意图。若用户只说“看看这个账号”，先问“看主页资料还是最近发帖”。
5. 没有平台时默认走通用搜索。优先 `exa_search_auto`；用户说“Google”时走 `apify_serp_scraperlink` 或 `apify_google_search_scraper`。
6. 多平台请求先确认范围。一次最多 3 个平台；超过 3 个时要求用户缩小范围。
7. 命中受阻端点时先解释，不执行。回复必须包含：原因、能否恢复、可用的 verified 替代端点。
8. 置信度不足时只问一个问题。给出最多 3 个选项，不执行采集。
9. 自由文本永远不直接执行采集。先出确认卡，用户确认后才调用 `collect_capability`。
10. 用户说“全部/所有/批量”时，先给数量和上限，再要求确认。

### 4.5 编排前检查清单

1. 查 `get_provider_status`，确认端点 availability 为 `verified`。60 秒缓存可以接受；确认卡执行前再查一次。
2. 查 `policy_block_reason`。非空时拒绝执行，回复原因。
3. 查 `missing_configuration`。非空时拒绝执行，回复缺什么。
4. 对 `public_feed`、`generic_web` 做 host 预检。用户 URL 的 host 不在批准列表时，执行前拒绝，不要等上游报错。
5. 校验必填参数。`required_params` 为空不等于无参数；部分端点有 `param_fields` 和默认输入。
6. 校验 `max_items`、`maxItems`、`resultsLimit`。给默认上限，防止一次拉取过多。
7. 检查用户额度、聊天额度、并发额度。
8. 生成确认卡。确认卡包含端点、参数摘要、预计条数、计费提示、状态、有效期。
9. 执行后按结果分类：success 且 records > 0、empty、degraded、policy、config、params。不同类别用不同回复。
10. 记录运行 ID、端点、参数哈希、用户 open_id、记录数、错误分类。不要在日志里写密钥。

## 5. 对话设计

### 5.1 两层结构

- **命令层**：确定性解析，零 LLM，零歧义。用于能力发现、详情、显式采集。
- **自由文本层**：意图识别 + 槽位抽取 + 确认卡。用于自然语言请求。
- **执行层**：只接受通过校验的 `endpoint_type` 和 `params`。执行层不解析自然语言，不调用 LLM。

### 5.2 命令层

现有命令已经可用：

| 命令 | 作用 | 是否消耗额度 |
|---|---|---|
| `帮助` | 显示用法 | 否 |
| `总览` | 能力统计与状态分布 | 否 |
| `平台 [关键词]` | 列出平台包 | 否 |
| `能力 <平台或关键词>` | 列出端点、状态、必填参数 | 否 |
| `详情 <端点>` | 参数、状态、坑点、最近实测 | 否 |
| `采集 <端点> [key=value ...]` | 立即采集 | 是 |

建议 P1 增加：

| 命令 | 作用 |
|---|---|
| `确认 <token>` | 执行确认卡中的采集 |
| `取消 <token>` | 放弃确认卡 |
| `运行 <run_id>` | 查询运行状态与记录数 |
| `额度` | 查看个人今日剩余额度 |
| `状态 <端点>` | `详情` 的别名，突出可用性 |

命令层的 `采集` 视为用户已确认，因为用户显式输入了端点名和参数。自由文本层不适用这条规则。

### 5.3 自由文本层

P1 先用规则路由，不接 LLM。

处理流程：

1. 清洗文本：去掉 `@_user_\d+`、`@_all`、全角标点，保留原始大小写用于展示。
2. 识别平台词：TikTok、抖音、X、Twitter、推特、Instagram、IG、YouTube、YT、Reddit、Threads、Facebook、FB、LinkedIn、领英、B站、哔哩哔哩、微博、知乎、快手、小红书、微信、公众号、Lemon8、Bluesky。
3. 识别动词：搜、找、查、看看、监测、追踪、对比、分析、提取、下载。
4. 识别对象：帖子、视频、直播、评论、账号、粉丝、热搜、趋势、广告、新闻、商品、价格、职位、公司、应用评论、网页、字幕。
5. 抽取槽位：关键词（引号内或“关于……的”）、账号（`@` 后或“账号”前）、URL、ID、国家、时间范围、条数。
6. 匹配意图表。命中多个意图时，按“平台 + 对象 + 动词”的具体度排序。
7. 命中受阻端点时，不执行，回复原因和替代。
8. 置信度低于阈值时，只问一个澄清问题，最多给 3 个选项。
9. 生成确认卡。用户确认后才执行。

示例：

- “搜一下 TikTok 上最近关于 AI 的视频” → 意图“社媒关键词搜索”，平台 TikTok，端点 `tikhub_tiktok_video_search`，参数 `keyword=AI`、`max_items=10`。
- “看看这个账号最近发了什么” → 如果文本里有 `@handle`，进入“账号最近发帖”；否则先问“账号名是什么”。
- “分析这条视频的评论” → 如果文本里有 URL，按平台选评论端点；没有 URL 时先要链接。
- “查一下这个 PDF” → 意图“文档解析”，回复“当前策略不可执行”，并说明需要 file_url 和策略评审。

### 5.4 确认与额度

**零额度动作**：帮助、总览、平台、能力、详情、运行查询、确认/取消提示、错误说明。

**消耗额度动作**：采集、批量采集、AI 问答、深度研究、任何 Apify、Exa、TikHub 端点。

确认流程：

1. 机器人生成确认卡，包含：意图名、端点、参数摘要、预计条数上限、计费提示、当前状态、有效期。
2. 确认卡带一次性 token。token 绑定 `open_id`、`chat_id`、`endpoint_type`、参数哈希。有效期 5 分钟。
3. 用户回复 `确认 <token>` 或点击卡片按钮。
4. 执行前重新检查 availability、policy、config、host、额度。
5. 执行后回复记录数、运行 ID、控制台链接、前 3 条样例字段。
6. 同一 token 只能执行一次。同一参数哈希在 60 秒内重复提交时，返回已有运行，不重复消耗额度。

额度建议：

- 单次默认 `max_items=10`。评论、商品评论、价格监控可设 5。
- 单次最多 50 条记录。超过时要求用户缩小范围。
- 单次批量最多 3 个端点。超过时要求分批。
- 每用户每日最多 20 次采集。每聊天每日最多 50 次。数值可配置。
- 成本未知时不自动执行。只允许管理员白名单内的端点，或要求二次确认并设置保守上限。
- 策略拒绝不自动重试。空结果不自动重试。参数错误不自动重试。

### 5.5 LLM 使用边界

P1 不使用 LLM。理由：

- 意图数量有限，规则路由可以覆盖主要说法。
- 端点名和参数必须精确，LLM 容易编造。
- 每次误采集都会消耗上游额度。
- 当前 `unknown` 分支已经有安全兜底，不会误执行。

P2 可以引入 LLM，但只做“规划器”：

- 输入：用户文本 + 精简的 verified 端点目录（端点名、说明、必填参数、返回类型）。
- 输出：JSON，字段为 `intent_id`、`endpoint_type`、`params`、`confidence`、`clarification`、`estimated_records`。
- 校验：端点必须在 verified 白名单；参数必须通过 required/optional 校验；置信度低于阈值时只问问题；任何一项不通过就拒绝执行。
- 确认：LLM 只生成计划，不执行。确认卡仍然由服务端生成，用户确认后才执行。
- 多步：最多 3 步；每步都必须是 verified 端点；任何一步受阻，整单拒绝，不执行前几步。
- 隔离：LLM 不接触 App Secret、Provider 密钥、内部主机名、原始上游错误。

### 5.6 回复格式

- 列表类：每行 `标题｜作者｜时间｜指标｜URL`。最多 10 行，超过时给“还有 N 条，回复‘更多’”。
- 详情类：键值行。包含状态、必填参数、可选参数、计费提示、最近实测、坑点。
- 采集结果：记录数、运行 ID、控制台链接、前 3 条样例字段。不要在飞书文本里塞原始 JSON。
- 错误类：原因、影响、下一步。例如“该端点受外访策略限制，不能通过参数恢复。可改用 `exa_search_auto` 或 `apify_google_news_scraper`。”
- 长度：飞书文本回复上限 6000 字符。现有 `_truncate` 已处理。P2 改为文件或卡片分页。
- 控制台链接：`{SHUSUO_CONSOLE_BASE_URL}/collect/{run_id}`。新 IA 会重定向到 `/runs/{run_id}`；P1 确认后改为新路径。

### 5.7 安全与权限

- 保留现有验签、AES 解密、verification token、app_id 校验、event_id 去重。
- 设置 `SHUSUO_ALLOWED_OPEN_IDS`。当前 `allowlist_size=0`，租户内任何人都能用。首期建议只放测试用户。
- 飞书后台只授予必要权限：接收消息事件、以应用身份发消息。不要授予通讯录、文档、表格等无关权限。
- App Secret 只放在服务端环境变量。本文不记录明文。该 Secret 已在对话中出现过，建议在飞书后台重置，并同步更新 `LARK_SHUSUO_APP_SECRET`。
- 如果飞书后台开启加密回调，设置 `LARK_SHUSUO_ENCRYPT_KEY`，并确认 `encrypt_enabled=true`。
- `/api/agents/shusuo/health` 会暴露 app_id、默认 project_id、白名单人数。建议只在内网或加鉴权后访问。
- 采集失败回复不要直接返回 `type(exc).__name__: exc`。P1 改为分类文案，原始错误只写日志。
- 文件消息继续拒绝，直到 anydoc 策略和 file_key 下载链路完成。

### 5.8 错误与降级

| 情况 | 回复 | 是否重试 |
|---|---|---|
| policy 拒绝 | 说明受外访策略限制，不能通过参数恢复；给替代端点 | 否 |
| 缺配置 | 说明缺哪个配置，且仍受策略限制 | 否 |
| degraded | 说明最近失败；给替代端点或建议稍后再试 | 不自动 |
| empty | 说明运行成功但 0 条；建议改关键词、时间范围或平台 | 不自动 |
| 参数错误 | 指出缺哪个必填参数，给 `详情` 命令 | 否 |
| 额度超限 | 说明单次/每日上限，建议缩小范围 | 否 |
| 上游超时 | 说明超时；建议减少条数或换端点 | 可一次 |
| 未知意图 | 给 3 个候选意图和 `帮助` | 否 |

| P1-9 | 运行查询 | `运行 <run_id>` 返回状态、记录数、控制台链接 |
| P1-10 | 测试补齐 | 意图路由、确认、额度、host 预检、受阻端点、重复事件 |

### P2 后续

| 优先级 | 事项 | 说明 |
|---|---|---|
| P2-1 | LLM 规划器 | 只做意图解析和计划生成；白名单、schema 校验、确认卡三层约束 |
| P2-2 | 多步研究 | 搜索 → 正文 → 摘要；最多 3 步；任一步受阻整单拒绝 |
| P2-3 | 异步长任务 | Apify 长 actor、深度研究；先持久受理，再返回运行 ID；进度卡片 |
| P2-4 | 定时监控与告警 | 独立 scheduler；quick-collect 是 `manual_refresh_only`，不能直接当定时任务 |
| P2-5 | 文件与数据集 | 飞书文件上传/下载、CSV/JSON 导出、数据集链接 |
| P2-6 | 策略与配置评审 | MediaCrawler、AnyCrawl、Twitter、Blackbird、BestBlogs、LLM key；先策略后配置 |
| P2-7 | OSINT 合规决策 | 受控出口、隐私合规、用途声明；默认关闭 |
| P2-8 | 可观测性 | 按意图统计成功率、空结果率、策略拒绝率、平均记录数、费用 |

### 优先级建议

- 首期不要投入 MediaCrawler、AnyCrawl、twscrape、Blackbird、BestBlogs、browser_use 的配置。它们全部同时被策略拦截，补配置不会提升可用能力。
- 首期把工程投入放在 165 个 verified 端点的意图编排、确认、额度和结果格式化。
- P2 的策略评审按业务价值排序：`generic_web`/`public_feed` 的 host 轮换 → Firecrawl/Jina 的结构化提取 → MediaCrawler 的 B站/微博/知乎/快手 → OSINT。
- 如果要提升“网页正文”能力，优先谈 Firecrawl/Jina 的受控出口，而不是继续找新的抓取端点。
